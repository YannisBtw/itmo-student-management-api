# ITMO Student Management — Web Programming Lab 2

Веб-приложение для управления данными студентов общежития, разработанное в рамках лабораторной работы по веб-программированию в ИТМО.

Проект является развитием первой лабораторной работы. В первой версии данные хранились непосредственно в браузере с использованием IndexedDB. Во второй лабораторной приложение было переработано в клиент-серверную архитектуру: frontend взаимодействует с REST API, реализованным на Flask, а данные сохраняются сервером в JSON-файл.

Приложение позволяет просматривать список студентов, добавлять новых студентов, редактировать существующих, удалять записи, просматривать подробную информацию и выполнять фильтрацию по нескольким параметрам.

# Общая информация

Проект представляет собой небольшую информационную систему для работы с данными студентов, проживающих в общежитиях.

Каждый студент представлен отдельной записью, содержащей:

- ФИО;
- учебную группу;
- ИСУ ID;
- номер общежития;
- номер комнаты;
- дату заселения;
- информацию о том, является ли студент иностранным;
- дополнительные заметки.

Пользователь взаимодействует с приложением через веб-интерфейс.

Frontend не работает с хранилищем напрямую. Все операции над данными выполняются через HTTP-запросы к Flask API.

---

# Цель проекта

Основной целью второй лабораторной работы является переход от локального browser-based приложения к полноценной клиент-серверной архитектуре.

В рамках работы были реализованы:

1. backend на Flask;
2. REST API;
3. серверная бизнес-логика;
4. серверная валидация;
5. JSON-хранилище;
6. CRUD-операции;
7. HTTP-коды ответа;
8. обработка ошибок;
9. фильтрация через query-параметры;
10. отдельный метод `QUERY`;
11. взаимодействие frontend и backend через `fetch`;
12. разделение приложения на слои.

# Основные возможности

Приложение поддерживает следующие операции:

### Просмотр списка студентов

Главная страница отображает таблицу со всеми существующими студентами.

Для каждого студента отображаются:

- ФИО;
- группа;
- ИСУ ID;
- общежитие;
- комната;
- дата заселения;
- действия.

---

### Добавление нового студента

Пользователь может открыть форму и создать новую запись.

Перед сохранением выполняется:

- HTML-валидация;
- frontend-валидация;
- серверная валидация.

---

### Редактирование студента

При открытии формы редактирования данные выбранного студента автоматически загружаются с backend и подставляются в поля формы.

После изменения отправляется HTTP-запрос `PATCH`.

---

### Удаление студента

Перед удалением приложение запрашивает подтверждение пользователя.

После подтверждения frontend отправляет:

```http
DELETE /api/students/:id
```

---

### Просмотр подробной информации

Для каждого студента доступна отдельная страница с полной информацией.

---

### Фильтрация

Можно фильтровать студентов по:

- группе;
- номеру общежития;
- статусу иностранного студента.

Можно использовать несколько фильтров одновременно.

# Архитектура приложения

Приложение построено по клиент-серверному принципу.

Общая схема:

```text
Browser
   │
   │ HTML / CSS / JavaScript
   │
   ▼
Frontend
   │
   │ fetch()
   │ HTTP + JSON
   ▼
Flask REST API
   │
   ▼
Routes
   │
   ▼
Services
   │
   ▼
Repository
   │
   ▼
students.json
```

Frontend не обращается к `students.json` напрямую.

Также frontend не содержит основной бизнес-логики проверки данных.

Сервер является главным источником истины для данных приложения.

Главная точка запуска приложения.

Файл:

- подключает API Blueprint;
- настраивает JSON;
- содержит маршруты frontend-страниц;
- содержит глобальный обработчик ошибки `500`;
- запускает Flask development server.

## `student_routes.py`

Слой маршрутизации.

Он отвечает за:

- получение HTTP-запроса;
- чтение path-параметров;
- чтение query-параметров;

- вызов сервисного слоя;
- формирование HTTP-ответа;
- выбор HTTP-кода.

Сервисный слой.

Содержит бизнес-логику приложения:

- создание студента;

- удаление;
- фильтрацию;
- валидацию;
- проверку уникальности ИСУ;
- генерацию нового ID.

Repository layer отвечает за работу с физическим хранилищем.

Слой:

- читает `students.json`;

- ищет студентов по ID;
- ищет студентов по ИСУ ID.

# Модель студента

Пример объекта студента:

```json
{
    "id": 1,
    "fullName": "Иванов Иван Иванович",
    "group": "P3120",
    "isuId": 505115,
    "dormitoryNumber": 8,
    "roomNumber": 305,
    "moveInDate": "2026-09-11",
    "isForeign": false,
    "notes": "Тестовый студент"
}
```

---

# Поля модели

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | Внутренний идентификатор записи |
| `fullName` | string | ФИО студента |
| `group` | string | Учебная группа |
| `isuId` | integer | Уникальный ИСУ ID |
| `dormitoryNumber` | integer | Номер общежития |
| `roomNumber` | integer | Номер комнаты |
| `moveInDate` | string | Дата заселения |
| `isForeign` | boolean | Является ли студент иностранным |
| `notes` | string | Дополнительные заметки |

---

# `id` и `isuId`

В приложении используются два разных идентификатора.

### `id`

Технический идентификатор записи.

Используется в URL:

```text
/api/students/1
```

---

### `isuId`

Предметный идентификатор студента.

Например:

```text
505115
```

ИСУ ID должен быть уникальным.

Пользователь может изменять `isuId`, но не может самостоятельно изменять технический `id`.

# REST API

Реализованы следующие операции:

| HTTP method | Endpoint | Назначение |
|---|---|---|
| `GET` | `/api/students` | Получить всех студентов |
| `GET` | `/api/students/:id` | Получить одного студента |

| `QUERY` | `/api/students` | Выполнить фильтрацию через JSON |

# PATCH — изменение студента

`PATCH` используется для изменения существующей записи.

Например:

```http
PATCH /api/students/2
```

Body:

```json
{
    "roomNumber": 800
}
```

Сервер объединяет новые значения с существующими и выполняет валидацию результирующего объекта.

---

Можно изменить несколько полей:

```json
{
    "roomNumber": 800,
    "notes": "Переселён в другую комнату"
}
```

---

## Response

```http
200 OK
```

# Работа фильтрации на frontend

Frontend собирает введённые значения:

```javascript
{
    group: "P3120",
    dormitory: "8",
    isForeign: "false"
}
```

После этого `URLSearchParams` превращает объект в:

```text
group=P3120&dormitory=8&isForeign=false
```

И выполняется:

```http
GET /api/students?group=P3120&dormitory=8&isForeign=false
```

Сам frontend студентов не фильтрует.

Фильтрацию выполняет backend.

# Валидация

Валидация выполняется на двух уровнях:

```text
Frontend
+
Backend
```

Frontend-валидация делает интерфейс удобнее для пользователя.

Backend-валидация гарантирует целостность данных.

---

# Валидация ФИО

ФИО должно:

- быть строкой;
- содержать минимум два слова;
- каждое слово должно содержать минимум два символа.

Корректный пример:

```text
Иванов Иван
```

Некорректные:

```text
Иванов
```

```text
И Иванов
```

---

# Валидация группы

Используется регулярное выражение:

```regex
[A-Z][1-9][1-4][0-9]{2}
```

Пример корректной группы:

```text
P3120
```

---

Структура:

```text
P 3 1 20
│ │ │ └── две цифры
│ │ └──── цифра от 1 до 4
│ └────── цифра от 1 до 9
└──────── заглавная латинская буква
```

---

# Валидация ИСУ ID

ИСУ должен:

- быть числом;
- содержать шесть цифр;
- находиться в диапазоне:

```text
100000–999999
```

Также ИСУ должен быть уникальным.

---

# Валидация номера общежития

Допустимый диапазон:

```text
1–99
```

---

# Валидация номера комнаты

Допустимый диапазон:

```text
1–9999
```

---

# Валидация даты заселения

Дата должна соответствовать формату:

```text
YYYY-MM-DD
```

Например:

```text
2026-09-11
```

Дата:

- не может быть раньше `01.01.1990`;
- не может быть позже текущей даты.

---

# Валидация `isForeign`

Поле должно иметь boolean-тип:

```json
true
```

или:

```json
false
```

Строки:

```json
"true"
```

```json
"false"
```

для JSON-body не считаются корректными boolean-значениями.

---

# Валидация заметок

`notes` должно быть строкой.

Если заметки отсутствуют, используется пустая строка:

```json
""
```

---

# Уникальность ИСУ ID

Уникальность ИСУ проверяется на backend.

При создании студента сервер ищет существующую запись с таким `isuId`.

Если она найдена:

```http
409 Conflict
```

Пример:

```json
{
    "error": {
        "code": 409,
        "message": "Студент с таким ИСУ ID уже существует"
    }
}
```

При редактировании сервер учитывает ID текущего студента.

Поэтому студент может сохранить собственный существующий ИСУ, но не может установить ИСУ другого студента.

---

# Почему уникальность проверяется на сервере

Frontend нельзя считать надёжным источником проверки данных.

Пользователь может:

- изменить JavaScript;
- отключить frontend-проверку;
- отправить запрос напрямую через `curl`;
- использовать Postman;
- отправить HTTP-запрос из другого клиента.

Поэтому критические ограничения обязательно должны проверяться сервером.

# HTTP-коды ответа

В проекте используются следующие HTTP status codes.

| Код | Название | Использование |
|---|---|---|
| `200` | OK | Успешный GET, PATCH или QUERY |
| `201` | Created | Успешное создание студента |
| `204` | No Content | Успешное удаление |
| `400` | Bad Request | Некорректный запрос |
| `404` | Not Found | Студент не найден |
| `409` | Conflict | Конфликт уникального ИСУ |
| `422` | Unprocessable Entity | Ошибки валидации данных |
| `500` | Internal Server Error | Неожиданная серверная ошибка |

# Формат ошибок

Для ошибок используется единый JSON-формат.

Пример:

```json
{
    "error": {
        "code": 404,
        "message": "Студент не найден"
    }
}
```

---

При ошибках валидации также могут передаваться подробности.

Пример:

```json
{
    "error": {
        "code": 422,
        "message": "Ошибка валидации",
        "details": {
            "group": "Некорректный формат группы",
            "roomNumber": "Номер комнаты должен быть числом от 1 до 9999"
        }
    }
}
```

# Проверка JSON

Для `POST`, `PATCH` и `QUERY` backend проверяет наличие JSON.

Если запрос не содержит JSON:

```http
400 Bad Request
```

---

Также проверяется, что JSON является объектом.

Корректно:

```json
{
    "group": "P3120"
}
```

Некорректно:

```json
[
    "P3120"
]
```

# Редактирование студента

Редактирование начинается со страницы:

```text
/student-form.html?id=3
```

Frontend получает:

```javascript
studentId = 3
```

Затем выполняется:

```http
GET /api/students/3
```

Полученные значения подставляются в форму.

После изменения отправляется:

```http
PATCH /api/students/3
```

---

# Почему используется PATCH

`PATCH` предназначен для частичного изменения существующего ресурса.

Например можно изменить только:

```json
{
    "roomNumber": 500
}
```

без необходимости передавать весь объект.

# Stateless-подход

REST API проекта является stateless.

Это означает, что каждый HTTP-запрос содержит всю информацию, необходимую серверу для его выполнения.

Например:

```http
GET /api/students/3
```

уже содержит ID нужного студента.

Серверу не требуется помнить предыдущий запрос клиента.

---

## Stateless не означает отсутствие хранения данных

Данные студентов сохраняются на сервере.

Stateless относится не к данным приложения, а к состоянию взаимодействия между клиентом и сервером.

Сервер не должен зависеть от истории предыдущих запросов клиента для обработки нового запроса.

# Разделение ответственности

Приложение разделено на несколько уровней.

## Routes

Отвечают за HTTP.

Например:

```text
GET
POST
PATCH
DELETE
QUERY
```

Routes не должны непосредственно заниматься физической работой с файлом.

---

## Service

Содержит бизнес-логику.

Например:

```text
проверить данные
проверить уникальность
создать ID
обновить студента
отфильтровать студентов
```

---

## Repository

Работает с хранилищем.

Например:

```text
прочитать JSON
записать JSON
найти студента
```

---

## Почему это полезно

Без разделения всё приложение могло бы находиться в одном огромном файле:

```text
app.py
```

Тогда:

- код сложнее читать;
- сложнее искать ошибки;
- сложнее расширять приложение;
- HTTP-логика смешивается с бизнес-логикой;
- работа с файлами смешивается с валидацией.

Разделение делает приложение более структурированным.

# Blueprint

API-маршруты вынесены в отдельный Flask Blueprint.

После этого Blueprint регистрируется в приложении:

```python
app.register_blueprint(student_routes)
```

Это позволяет не хранить все API-маршруты непосредственно в `app.py`.

Пример:

```python

    ...
```

Декоратор связывает URL и Python-функцию.

# Запрет изменения ID

Технический `id` не входит в список разрешённых пользовательских полей.

Таким образом запрос:

```json
{
    "id": 100
}
```

не должен менять ID существующего студента.

---

# Проверка boolean

В Python существует особенность:

```python
isinstance(True, int)
```

возвращает:

```python
True
```

Поэтому при проверке числовых полей дополнительно исключается `bool`.

Например:

```python
not isinstance(value, int)
or isinstance(value, bool)
```

Это предотвращает принятие:

```json
true
```

вместо номера общежития или ИСУ.

```text
   - style.css
   - db.js
   - students.js

5. students.js вызывает getAllStudents()

6. db.js выполняет:
   GET /api/students

7. Flask API получает запрос

8. Repository читает students.json

9. API возвращает JSON

10. students.js создаёт таблицу через DOM

11. Пользователь нажимает «Редактировать»

12. Browser открывает:
    /student-form.html?id=1

14. Выполняется:
    GET /api/students/1

15. Backend возвращает данные

16. form.js заполняет поля

17. Пользователь меняет данные

18. Нажимает «Сохранить»

19. Выполняется:
    PATCH /api/students/1

20. Backend проверяет данные

21. Repository сохраняет JSON

22. Frontend возвращает пользователя на главную страницу
```

# Почему CORS не требуется

Frontend и backend работают с одного origin:

```text
http://127.0.0.1:5000
```

Frontend:

```text
http://127.0.0.1:5000/
```

API:

```text
http://127.0.0.1:5000/api/students
```

Поэтому отдельная настройка CORS для текущей архитектуры не требуется.

---

# Почему API URL относительный

Во frontend используется:

```javascript
const API_URL = "/api/students";
```

а не:

```javascript
const API_URL =
    "http://127.0.0.1:5000/api/students";
```

Это позволяет frontend обращаться к тому же серверу, с которого была загружена страница.

# Почему в учебной версии используется JSON

JSON-хранилище достаточно для демонстрации:

- клиент-серверной архитектуры;
- REST API;
- CRUD;
- маршрутизации;
- HTTP;
- сериализации;
- серверной логики;
- Repository layer.

При этом оно не требует отдельной СУБД и позволяет сосредоточиться на архитектуре веб-приложения.

---

# Ограничения JSON-хранилища

JSON-файл не предназначен для высоконагруженных production-систем.

При большом количестве параллельных запросов потребуется полноценная база данных с поддержкой:

- транзакций;
- блокировок;
- индексов;
- конкурентного доступа.

Для лабораторной работы JSON является простым и наглядным вариантом хранения.
